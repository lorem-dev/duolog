# How sync keeps agents and skills in step

`duolog sync` generates one agent's skills and agent files from the other's
sources.

## How to choose the direction

Run this once. It names the side that holds the sources:

```bash
duolog sync --from claude
```

Use `--from codex` for the other direction. duolog saves the direction in
`.duolog/sync.lock.json`. Later runs need no flag.

To reverse the direction, add `--switch-direction`. duolog then rebuilds the
old sources from the new ones.

## What sync writes

| Source | Target |
|---|---|
| `.claude/skills/<name>/SKILL.md` | `.agents/skills/<name>/SKILL.md` |
| `.claude/agents/<name>.md` | `.codex/agents/<name>.toml` |

The Codex skills folder is `.agents/skills` unless `agents.codex.skills_dir`
names another one, such as `.codex/skills`. See
[Configuration](configuration.md#where-codex-keeps-its-project-skills).

With `--from codex`, reverse the arrows. Outputs are regular files, never
symlinks; generated skills carry `# Generated by duolog sync. Do not edit.`
The lock records source paths and source/target hashes.

## What sync changes in an agent file

| Field | Rule |
|---|---|
| Model | Mapped by `sync.agents.model_map`: `opus` to `sol`, `sonnet` to `terra`, `haiku` to `luna`, `fable` to `astra` |
| Effort | Taken from the source, or from `default_effort`, then translated with `effort_map` |
| Name | Kept as it is, unless `codex_name` is `underscore` |
| Unknown key | Sync refuses the file, so nothing is lost without a message. `color` is dropped by default |

Skills keep every key, because both agents ignore keys they do not know. Sync
warns when a Claude skill sets `disable-model-invocation`, because Codex does
not honor it.

## How to preview and check

| Flag | Effect |
|---|---|
| `--dry-run` | Prints what would change and writes nothing |
| `--check` | Writes nothing and exits 1 if a generated file is out of date or refused |
| `--agents-only`, `--skills-only` | Limit the run |
| `--path <file>` | Sync only the agent or skill that holds this path |
| `--model opus=terra` | Map one alias for this run |
| `--force` | Overwrite a generated file that you edited by hand |

## When sync refuses a file

Edited targets are refused with exit 1. Fix the source or use `--force` to
restore the generated version.

Sync skips duolog's own skill folders on both sides; install owns their
user-scope copies. Backslashes work in `--path`, including
`duolog sync --path .claude\agents\review.md` in PowerShell.

## How hooks run sync

With `sync.auto: true`, a main session runs sync after a tool call that edits
a skill or an agent, and at session start. It does nothing until you choose a
direction. Worker sessions never run sync.

## What remains unverified

- Codex loads project agent files only in a trusted folder. Sync prints a
  note when it writes a Codex agent and the folder is not trusted.
- In an earlier run, Claude did not apply `effort` from agent frontmatter.
  That is NOT VERIFIED. duolog passes the effort at run time.
- Real agent-driven sync on Windows has not been run.

## How concurrent hooks share state

Sync holds `.duolog/sync.lock` while reading ownership, generating files and
saving the lock. A source scan error reports a conflict and prevents stale
file removal. Matching bytes do not make a hand-placed file owned by duolog.

Linked worktrees generate in their own checkout. Their ownership records live
under the main checkout's `.duolog/worktrees/`, so edits in one tree do not
change another tree's file hashes. The first sync in a linked worktree starts
from the `.duolog/sync.lock.json` in that checkout, so generated files that
the repo commits stay owned by duolog. When a lead session starts, duolog
removes the records of worktrees that Git no longer lists.
